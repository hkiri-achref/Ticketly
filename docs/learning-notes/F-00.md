# F-00 — Repository, infrastructure and first ADR

## What was built
The whole local platform from one command: `infra/docker-compose.yml` with
four Postgres 17 containers (one per future service, own volume and
credentials each), Kafka 4 (single-node KRaft), Keycloak 26 (realm `ticketly`
configured by hand in the UI, then exported to
`infra/keycloak/import/realm-export.json` and auto-imported on start),
Mailpit and grafana/otel-lgtm. Plus `infra/kafka/create-topics.sh`,
ADR 0001 (why microservices), README, `http/keycloak.http`. The leftover
root Maven project was deleted — the monorepo has no root build.

## Concepts practiced
- **Container vs. volume lifecycle**: a container's filesystem dies with it;
  a named volume survives `down`, recreate and image upgrades. Proven live:
  Keycloak kept its realm across stop/start; deleting the volume was the only
  way to lose it — and then `--import-realm` rebuilt it from the committed JSON.
- **Database-per-service, physically**: separate process, credentials, volume,
  failure domain per service — not just four schemas on one server. In prod
  this becomes managed instances (RDS) or a K8s operator, still one per service.
- **Healthchecks = readiness probes**: "process up" ≠ "ready". `pg_isready`,
  a broker API call for Kafka, and a bash `/dev/tcp` probe for Keycloak
  (its image ships no curl; health lives on management port 9000 since KC 25).
- **KRaft**: Kafka 4 has no ZooKeeper at all; the Raft controller is built in.
  Advertised listeners must match the client's network viewpoint — hence
  EXTERNAL `localhost:9092` (host apps) vs INTERNAL `kafka:29092` (containers).
- **OIDC vocabulary by hand**: realm, realm roles, public client + PKCE,
  direct access grants (dev-only password grant), claims (`sub`,
  `preferred_username`, `realm_access.roles`), issuer, JWKS via the
  discovery document.
- **Gotchas hit for real**: exporting while Keycloak runs fails (embedded H2
  file lock — stop the server, export via a one-off container); Docker turns
  a bind-mounted *missing file* into an empty directory (hence mounting the
  `import/` folder, not the file).

## Two interview questions I can now answer
1. *"Would you run Postgres in containers in production?"* — Containers in
   dev for one-command reproducibility; in prod, managed services or a K8s
   operator (CloudNativePG), because plain containers have no failover,
   replication or backup story. Either way: one database per service.
2. *"Why did you split the monolith, and what did it cost you?"* — Load/risk
   profiles, failure isolation, team ownership, auditability (ADR 0001);
   paid for with sagas instead of transactions, duplicated data, network
   failure handling and real operational complexity.

## One production concern deliberately simplified
No TLS anywhere, dev-mode Keycloak on H2, plaintext Kafka, passwords in the
compose file and a committed realm export containing (hashed) dev credentials.
Fine for a laptop; every one of these is a finding in a real environment —
secrets hygiene is addressed in F-23.
