# F-01 — catalog-service skeleton

## What was built
The first Spring Boot 4.1 service: `catalog-service` boots on Java 25 with
virtual threads, connects to its own Postgres through Docker Compose support
(it can start `catalog-db` by itself), applies an empty Flyway `V1`, exposes
`GET /api/v1/ping` + Swagger UI + actuator health, and passes one
Testcontainers-backed `@SpringBootTest`. It is the template for every later
service.

## Concepts practiced
- **Boot 4 starter anatomy.** Several renames vs Boot 3: `spring-boot-starter-webmvc`
  (was `-web`), a *per-starter* test dependency each (`…-webmvc-test`,
  `…-data-jpa-test`, …) instead of one `spring-boot-starter-test`, and
  `spring-boot-starter-flyway`. Testcontainers is now 2.x: containers live in
  `org.testcontainers.postgresql` and `PostgreSQLContainer` is no longer generic.
- **`spring.threads.virtual.enabled=true`.** MVC keeps thread-per-request, but
  on virtual threads — blocking JDBC no longer pins a scarce platform thread.
  This one flag is why staying fully blocking is a defensible architecture.
- **`@ConfigurationProperties` on a record.** Boot binds through the canonical
  constructor → immutable config; `@Validated` + `@NotBlank` turn a missing
  property into a startup failure instead of a runtime null.
- **`@ServiceConnection`.** The Testcontainers bean itself publishes its JDBC
  URL/credentials to Spring — no `@DynamicPropertySource` copying.
- **Docker Compose support against a shared file.** One compose file, four
  postgres containers: each service activates only its own **Compose profile**
  (`spring.docker.compose.profiles.active=catalog`). `infra/.env` sets
  `COMPOSE_PROFILES` so the plain `up -d` still starts everything.
  Gotcha found live: the default `start.skip=if-running` never runs `up` if
  *any* project container is running, so a stopped `catalog-db` stayed down
  while Kafka/Keycloak were up → `start.skip=never` (idempotent `up` each run).
- **Flyway with an empty migration.** Even `V1` containing only a comment makes
  Flyway create `flyway_schema_history` — migration history is infrastructure
  that exists before the first real table.

## Interview questions I can now answer
1. *"Why are your JPA entities classes while everything else is a record?"* —
   JPA needs a no-arg constructor, mutable fields, ID-based identity and
   proxy subclassing; records are final, immutable, value-based. Records fit
   DTOs, commands, events, projections and config, where immutability is a
   feature.
2. *"How does Spring Boot's Docker Compose support decide which container
   backs your DataSource?"* — It matches running compose services by image to
   `ConnectionDetails` factories, scoped by the active compose profile; the
   generated connection details take precedence over `spring.datasource.*`
   properties (which remain as a fallback when compose support is off).

## One production concern deliberately simplified
Credentials are plaintext in `application.yml` and the compose file, and the
service trusts whatever is on `localhost`. Real deployments inject secrets
(vault/K8s secrets — F-23) and get connection config from the environment,
not from a checked-in file.
