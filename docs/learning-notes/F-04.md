# F-04 — Event lifecycle: publish and cancel

## What was built
- `Event.publish()` and `Event.cancel(reason)` return a **sealed**
  `TransitionResult` (`Ok(event)` or `Rejected(reason, currentStatus)`), with
  a `RejectionReason` enum: `NO_TIERS`, `STARTS_IN_PAST`, `ALREADY_PUBLISHED`,
  `ALREADY_CANCELLED`. CANCELLED is terminal; `update` / `addTier` on a
  cancelled event throw `EventNotEditableException` (422).
- `@Version long version` on `Event`, plus `cancellation_reason` and
  `cancelled_at` (`V4__event_lifecycle.sql`, with a check constraint tying
  the two columns to `status = 'CANCELLED'`).
- `POST /api/v1/events/{id}/publish` and `POST /api/v1/events/{id}/cancel`.
  The controller switches exhaustively over the result with record patterns:
  `Ok` → 200, `Rejected` → 422 (`NO_TIERS`, `STARTS_IN_PAST`) or 409
  (`ALREADY_*`). `ObjectOptimisticLockingFailureException` → 409.
- Kafka `EventPublished` is a `TODO: F-15` in `Event.publish()` and
  `EventService.publish()`.

## Concepts practiced

### Sealed interface + records + exhaustive switch
`sealed interface TransitionResult permits Ok, Rejected` tells the compiler
the complete list of subtypes. A `switch` over it therefore needs no
`default`, and adding a third outcome fails compilation at every switch
that forgot it. Record patterns (`case Ok(var event) ->`) test the subtype
and destructure it in one line, so there is no `instanceof` + cast. The same
holds for the inner `switch (reason)` over the enum.

### Sealed result vs exceptions — when I would prefer exceptions
The sealed result won here because a rejected publish is an **expected**
answer with a distinct client action per reason, and the caller is one
level away (controller → service → entity). I would prefer exceptions when:
- the failure must **roll back** a transaction that already did work
  (a returned value does not trigger rollback; a `RuntimeException` does);
- the outcome has to travel through many layers that do not care about it
  (every layer would otherwise have to pass the result along);
- the failure is a **caller bug**, not a business outcome. That is exactly
  why editing a CANCELLED event throws `EventNotEditableException` while
  publishing it returns `Rejected`.
Rule of thumb: model the outcomes the client chooses between as a sealed
type; model "you should not have called this" as an exception.

### Optimistic locking end to end
1. Hibernate reads `version` with the row.
2. At flush it emits `update events set ..., version = 1 where id = ? and
   version = 0`.
3. If another transaction committed first, the row is at version 1, zero
   rows match, Hibernate throws `StaleObjectStateException` (wrapped in JPA's
   `OptimisticLockException`).
4. `JpaTransactionManager` translates it on commit into Spring's
   `ObjectOptimisticLockingFailureException`, so the service method throws
   it **after** its body has returned (the flush happens at commit).
5. The advice maps it to 409. No retry in the service: the transaction is
   gone and only the client knows whether its intent still makes sense.
Gotcha seen in the test: **every** flushed change bumps the version, not
just the "interesting" ones. Adding a tier bumped it before publish did.
Bonus: F-03's check-then-act gap in `addTier` is now closed for free.

### Deterministic concurrency test
Two virtual threads, each with its own `TransactionTemplate`, both load the
row, then a `CountDownLatch(2)` blocks each until the other has loaded. Only
then do both publish and commit. Exactly one throws. Without the latch the
second thread might load after the first committed and simply be rejected
with `ALREADY_PUBLISHED`, and the test would be flaky.

### 409 vs 422
- **422 Unprocessable Content**: the request is well formed and the resource
  exists, but a rule about the resource's own data is broken and the client
  can fix the data (add a tier, move the date).
- **409 Conflict**: the request conflicts with the **current state** of the
  resource. Both "it is already cancelled" and "someone else changed it
  since you read it" are the same category: reload, then decide again.

### `ResponseEntity<Object>` in the controller
The two switch arms produce different bodies (`EventResponse` vs
`ProblemDetail`). A `ProblemDetail` body is serialised as
`application/problem+json`; the content type is set explicitly so the
intent is visible.

## Interview questions I can now answer
1. **How does optimistic locking work in JPA, and how do you surface it to
   an HTTP client?** `@Version`, the `where version = ?` UPDATE, the
   exception chain Hibernate → Spring at commit time, and 409 with a
   "reload and retry" contract. Why not pessimistic: no lock held across a
   web request, and conflicts are rare.
2. **When would you model business outcomes as a sealed result type instead
   of exceptions?** Expected outcomes with distinct client actions, one
   layer away, no rollback needed → sealed type with exhaustive switch.
   Caller bugs, rollback needed, deep stacks → exceptions.

## Production concern deliberately simplified
The client cannot send `If-Match: "<version>"` yet. Today a 409 only
happens when two writes actually collide inside the database window. A
real API would also let a client say "publish version 3 or fail", so a
stale UI cannot act on a state it no longer sees. `version` is already in
`EventResponse` precisely so an ETag / `If-Match` scheme can be added
without changing the domain.
