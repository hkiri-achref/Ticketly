# F-03 — Events and ticket tiers (aggregate modeling)

## What was built
The catalog's first real aggregate: `Event` (root) owning a list of
`TicketTier` children, priced with a `Money` embeddable record. Flyway
`V3__events_tiers.sql` (two tables, FK, `(status, starts_at)` index),
`EventRepository` with an `@EntityGraph` finder, three command records,
`EventService` (create / update / addTier / getById), request and response
records, `EventController` (`POST /events`, `PUT /events/{id}`,
`POST /events/{id}/tiers`, `GET /events/{id}`) and a 422 `ProblemDetail`
mapping for the new `DomainRuleViolationException` hierarchy.

## Concepts practiced
- **Aggregate boundary.** `TicketTier`'s constructor is package-private and
  there is no `TicketTierRepository`: the only way to create, change or
  delete a tier is through `Event`. That is what makes the capacity rule
  (`sum(quantity) ≤ venue.capacity`) impossible to bypass — it has exactly
  one home, `Event.addTier`, and it reads the capacity from the referenced
  `Venue` instead of trusting a number passed in.
- **cascade = ALL + orphanRemoval = true.** Saving the event inserts its
  tiers; removing a tier from `event.tiers` deletes the row at flush with no
  repository call. The migration deliberately has no `on delete cascade` so
  the test proves JPA did it, not Postgres.
- **LAZY vs EAGER and `LazyInitializationException`.** `@ManyToOne` defaults
  to EAGER, so both `TicketTier.event` and `Event.venue` spell out LAZY.
  `@OneToMany` is LAZY by default. With OSIV off, `findById` outside a
  transaction returns a detached event whose `tiers` bag explodes on first
  access — reproduced in
  `EventRepositoryTest.given_findById_when_tiersAccessedOutsideTx_then_lazyInitializationException`
  using `@Transactional(propagation = NOT_SUPPORTED)` on the test method and
  a `TransactionTemplate` for the committed setup.
- **Two fixes for the lazy problem, one kept.**
  1. `@EntityGraph(attributePaths = "tiers")` on a derived query (kept):
     declarative, reuses the derived-query name, Hibernate emits one
     `select … left join ticket_tiers`.
  2. JPQL `join fetch` (equivalent, not kept):
     ```java
     @Query("select e from Event e left join fetch e.tiers where e.id = :id")
     Optional<Event> findWithTiersById(@Param("id") UUID id);
     ```
     Same SQL, explicit query text. Prefer it when the fetch shape needs
     conditions the graph cannot express, or when you want the SQL visible
     in the code. Both are a per-query override of the mapping's LAZY, which
     is the right granularity: EAGER on the mapping would load tiers for
     every event query forever (the N+1 door). One more subtlety: fetching a
     `List` bag is fine, but fetch-joining two bags at once throws
     `MultipleBagFetchException` — use `Set` or two queries then.
- **Dirty checking.** `update` and `addTier` load, call a domain method and
  return; there is no `save`. The entity is managed inside the transaction,
  so Hibernate diffs it at commit and issues the UPDATE / INSERT itself.
  `EventServiceTest` pins that with `then(events).should(never()).save(any())`.
- **Assigned ids and `save()` = `merge()`.** Discovered while writing the
  orphanRemoval test: because the UUID is assigned in the constructor,
  Spring Data's `isNew()` returns false and `save()` calls `em.merge`,
  which SELECTs, copies the state into a new managed instance and returns
  that copy — the original stays detached. Working on the original changed
  nothing. Consequences: (a) always use the instance `save` returns;
  (b) every insert costs an extra SELECT. The production fix is
  `implements Persistable<UUID>` with an `isNew()` flag cleared by
  `@PostPersist`/`@PostLoad` — deliberately not built here (see below).
- **ID-only `equals`/`hashCode` and `HashSet`.** `given_eventInHashSet_when_persisted_then_stillContained`:
  because the id exists before persist, the hash never changes and the set
  still finds the entity — and also finds a *different* instance reloaded
  from the database with the same id. With a DB-generated id the hash would
  flip from `hash(null)` to `hash(id)` on persist and `contains` would lie.
- **Record embeddable with a compact constructor.** `Money` validates
  (non-null, non-negative, scale ≤ 2, `[A-Z]{3}`) and normalises to two
  decimals so `10` and `10.00` are equal. Hibernate rebuilds it through the
  canonical constructor on load, so a corrupt row cannot become a `Money`.
  `@AttributeOverride` (repeatable since JPA 2.2) maps the components to
  `price_amount` / `price_currency`.
- **PMD taught something too:** `Event.tiers` is `final`. The reference never
  changes, only the contents, and Hibernate still injects its
  `PersistentBag` through reflection (final instance fields are writable
  that way except in records/hidden classes).
- **422 vs 400 vs 404.** Validation (shape) → 400 with `errors[]`; missing
  resource → 404; well-formed request that a business rule rejects → 422.
  Spring 7 names the constant `HttpStatus.UNPROCESSABLE_CONTENT` (RFC 9110);
  `UNPROCESSABLE_ENTITY` is deprecated.

- **Package layout: layer first, then aggregate.** Flat `api/` and `domain/`
  folders were already mixing requests, responses, controllers and handlers.
  Each layer now has one sub-package per aggregate root (`event`, `venue`) plus
  `common` for shared pieces (`Money`, the exception base, the advice). A
  service and its command records sit together because a command is simply
  the typed input of that use case. `ArchitectureTest` (ArchUnit) turns the
  rule into a test: no class at a layer root, no upward dependency — which is
  how the `VenueService`-imports-a-request-record slip from F-02 was caught
  and replaced by `CreateVenueCommand`.

## Interview questions I can now answer
1. *How do you design a JPA aggregate so invariants cannot be bypassed?*
   One repository per aggregate root; children have package-private
   constructors and are created only by root methods; child collections are
   exposed unmodifiable; `cascade`/`orphanRemoval` bind child lifecycle to
   membership in the parent; the invariant reads its inputs (here venue
   capacity) from the object graph, not from parameters.
2. *What causes `LazyInitializationException` and what are the trade-offs of
   each fix?* A lazy association touched after the session closed (OSIV off,
   entity detached). Fixes: `@EntityGraph` or `join fetch` per query (precise,
   but you must know what the caller needs); EAGER on the mapping (global,
   silently loads for every query, N+1 risk); DTO projection (fastest, no
   entity at all, but the domain method cannot run on it); OSIV on (hides the
   problem, holds a connection for the whole request). Rule of thumb: decide
   the fetch shape where the transaction is, i.e. in the service.

## Production concern deliberately simplified
Two related gaps, both scoped to F-04:
- **Check-then-act capacity rule.** Two concurrent `addTier` calls can each
  read "6000 allocated of 6293" and both insert 200. `@Version` on `Event`
  (optimistic locking) makes the second commit fail; F-04 adds it together
  with the state-transition rules that also need it.
- **`save()` is a `merge()`** for every new entity (assigned UUID), costing
  an extra SELECT per insert. `Persistable<UUID>` fixes it; left out to keep
  F-03 focused on the aggregate lessons.
Also unchanged from F-02: no security (`organizerId` is the placeholder
`"dev-organizer"` until F-07), and `PUT` does not yet refuse non-DRAFT events
because nothing can leave DRAFT before F-04.
